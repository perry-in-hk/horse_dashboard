## 一句話

同一台 Linode 上，點餐站和賽馬站都要開。對外只有一組 80 和 443，必須只留 `mia_ordering-caddy-1`。賽馬站的 `hkjc-caddy` 一啟動就會搶埠，兩個站會有一個進不去。

`hkjc-caddy` 維持停止。這是 2026-07-07 就定下的規則，見桌面知識庫 `DUAL_SITE_ARCHITECTURE.md`。

## 這次在做什麼

賽馬站程式更新到 `51b5353`（`cursor/council-betting-revamp-4d50`）：沒有可放行注時，共識卡仍顯示一注獨贏，標記「未達最佳」。在伺服器 `/root/horse_dashboard` 拉下這個分支後執行 `docker compose up -d --build`。

## 問題怎麼出現

1. Compose 會一併建立 `hkjc-caddy`，並把主機的 80、443 綁給它。
2. 這兩個埠已經是 `mia_ordering-caddy-1` 的。新容器報錯：

```text
Bind for 0.0.0.0:80 failed: port is already allocated
```

後來又變成 `Bind for :::80 failed`（IPv6 萬用位址）。

3. 當時 `docker ps` 的 `PORTS` 欄是空的，但 `curl http://127.0.0.1/` 仍回 Caddy 的 `308`。原因是舊的 `docker-proxy` 還聽著 80/443，轉到容器 IP `172.18.0.2`。`docker port hkjc-caddy` 沒有輸出，表示這個賽馬站 Caddy 自己沒有綁到埠。

4. 那些 `docker-proxy` 的指令列帶 `-use-listen-fd`。聽埠的檔案描述符在 Docker 主程式裡。只 `kill` proxy 不會把埠還出來，Docker 的埠配置表仍認為 80/443 已佔用。

5. 接著執行了 `systemctl restart docker`。資料庫 volume 沒有被刪，但所有容器都停過。起來的順序變成點餐站的 Caddy 先佔 80/443。賽馬站的 postgres、backend、scraper、recommender 一度是 Exited。`hkjc-caddy` 停在 `Created`。

6. 佔埠者用 `ss` 對到的 cmdline 是 `docker-proxy ... -container-ip 172.18.0.2 -host-port 80/443`。容器清單裡帶 `0.0.0.0:80->80/tcp` 的是 `mia_ordering-caddy-1`，不是 `hkjc-caddy`。

## 錯誤做法（不要再做）

| 做法 | 後果 |
|------|------|
| 在 `/root/horse_dashboard` 執行 `docker compose up -d` 或不帶服務名稱的 `--build` | 啟動 `hkjc-caddy`，和點餐站搶 80/443 |
| `docker rm` 之後 `kill` docker-proxy，立刻再建 `hkjc-caddy` | 埠仍被 Docker 記成已佔用，或被另一個站的 proxy 佔住 |
| `systemctl restart docker` 來「清埠」 | 兩個專案一起重啟；誰先綁到 80/443 誰贏。這次是點餐站先拿到 |
| 停掉 `mia_ordering-caddy-1` 把埠讓給賽馬站 | 點餐站 `miapet.cc.cd` 會斷線。兩個站都要留，所以不能這樣做 |
| 把 Caddyfile 片段直接貼進 bash | `handle: command not found`。檔案不會被改到 |
| 重啟 Mia Caddy 時不帶 `--env-file .env.production` | `DOMAIN` 空白，點餐站全站 502 |

`VITE_MESSENGER_PAGE_ID is not set` 只是點餐站一個空變數警告，不是這次故障的原因。

## 實際修復

操作者當時已是 `root@localhost`。點餐站目錄是 `/home/deploy/mia_ordering`，不是 root 的 `~/mia_ordering`。

### 1. 賽馬站內部服務（不含 Caddy）

```bash
cd /root/horse_dashboard
docker compose up -d postgres redis backend frontend scraper recommender
docker rm -f hkjc-caddy
```

結果：`hkjc-postgres`、`hkjc-backend` healthy；frontend、redis、scraper、recommender Up。`hkjc-caddy` 已刪除，不再佔埠。

### 2. 讓點餐站 Caddy 看見賽馬站網路

Docker 重啟或 Caddy recreate 之後，這條額外網路不一定還在。

```bash
docker network connect horse_dashboard_default mia_ordering-caddy-1 2>/dev/null || true
docker exec mia_ordering-caddy-1 wget -qO- http://hkjc-backend:4000/health
```

當時已回 `{"ok":true,"service":"backend"}`。

### 3. 補上議會 WebSocket

桌面知識庫 2026-07-07 的 HKJC 區塊只有 `/api`、`/health` 和前端。現行程式的議會走 `/ws/council`。`grep` 當時只看到第 37 行 `lord-in-hk.ccwu.cc {`，沒有 `ws/council`。

用 Python 寫進檔案（不要把 Caddy 語法貼進 shell），插在 `reverse_proxy hkjc-frontend:5173` 那個 `handle` 之前：

```caddyfile
    handle /ws/council* {
        reverse_proxy hkjc-backend:4000 {
            flush_interval -1
        }
    }
```

檔案路徑：`/home/deploy/mia_ordering/deploy/Caddyfile`。

然後：

```bash
cd /home/deploy/mia_ordering
docker compose -f docker-compose.prod.yml --env-file .env.production restart caddy
docker network connect horse_dashboard_default mia_ordering-caddy-1 2>/dev/null || true
```

`restart` 之後一定要再 `network connect` 一次。

## 驗證（2026-09-26，伺服器本機）

| 檢查 | 結果 |
|------|------|
| Caddyfile | 第 37 行 `lord-in-hk.ccwu.cc`，第 44 行 `handle /ws/council*`，腳本印出 `inserted` |
| 容器內 health | `wget` `hkjc-backend:4000/health` → `{"ok":true,"service":"backend"}` |
| 賽馬站經 Caddy | `curl --resolve lord-in-hk.ccwu.cc:443:127.0.0.1 https://lord-in-hk.ccwu.cc/health` → 同一個 JSON |
| 點餐站經 Caddy | `curl --resolve miapet.cc.cd:443:127.0.0.1 https://miapet.cc.cd/home` → `HTTP/2 200` |
| 對外 Caddy | 仍是 `mia_ordering-caddy-1`。`hkjc-caddy` 不存在 |

用 `https://127.0.0.1/` 只加 `Host` 標頭時，TLS 的 SNI 仍是 `127.0.0.1`，Caddy 可能對不上站點。本機驗證要用 `--resolve 域名:443:127.0.0.1`。

程式版本：`git log -1` 為 `51b5353`。後端在修復前已重建，health 來自這個行程。瀏覽器登入與議會頁這次沒有在外網點過。
